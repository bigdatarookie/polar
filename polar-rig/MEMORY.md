# Память и контекст финансового рига

## v0.27 — Полезный выход и данные диагностики

Lead использует существующие native queue transitions, PR timestamps, execution receipts и experiment registry для времени ожидания QA, времени исправлений, отказов до начала сценария и завершенных экспериментов. Календарное время не объявляется активной работой/токенами; строки кода и число qitems не являются целью. Нужны компактный текущий вывод и ссылки, не новый tracker или журнал каждого действия. Проверка без отклонений не записывается. Существенная находка в существующих process-health NOTES содержит препятствие, предпринятое действие и наблюденный эффект; запись правила/доставка контекста не доказывают восстановления.

Этот файл — политика, не накопительный журнал. Существующие примитивы OpenRig используются по назначению. Встроенная структура проверена по установленному 0.7.7; оператор повторяет проверку на версии запуска.

## Единственные источники правды

### v0.25 — Существенный опыт вместо журнала каждой попытки

Использовать существующие нативные места и действующие token/retrieval budgets: mission/slice NOTES.md — существенная проблема, причина выбора решения, наблюдаемый результат, ограничения и evidence; LEARNED.md соответствующего seat/pod/rig — переносимый вывод, который изменит действие при похожем случае, с условиями применимости. Повторяемое решение полезнее закрепить кодом, инструментом или инструкцией. Не копировать эпизод целиком на все уровни, не заводить новую БД/журнал/сущность и не расширять обязательный boot context. Queue остается источником текущей ответственности. Журнал process-health сохраняет специальный scope существенных отклонений, access-журнал — scope эпизодов доступа; общие уроки их не дублируют.

Перед похожей задачей читать релевантный компактный вывод и проверять актуальность предпосылок. Запись знания сама по себе не доказывает обучение: при повторении применять проверенный способ или явно объяснять, почему условия изменились. Отмечать наблюденный эффект отдельно от предполагаемой причины; непроверенное решение остается UNVERIFIED, не становится общей инструкцией как доказанное. Ошибочный вывод исправлять связанной записью с сохранением истории. Не требовать отчет о каждом поиске или неудачной команде; сохранять только существенное для продолжения и предотвращения повторов, без секретов/raw data.

| Вид информации | Канонический владелец/артефакт | Финансовое дополнение |
|---|---|---|
| Ценности команды | Нативная цепочка `CULTURE.md` | Короткая финансовая культура из этого пакета, без повторения SOP |
| Намерение и требования | Нативные project/mission/slice `SPEC.md` и manifests | Ссылка на версию финансового контракта |
| Назначение, текущая ответственность, blocker, handoff | Queue/inbox/workflow OpenRig | Ссылка из эксперимента на qitem/scope, без копирования task state |
| Опыт конкретного seat/pod/rig | Нативная цепочка `LEARNED.md`, нужный уровень | Краткие выводы, причины, ссылки на эксперименты |
| Ход работы в scope | Нативный `NOTES.md` | Полевые наблюдения, не альтернативный task tracker |
| Доказательство и приемка scope | `PROOF.md`, evidence и proof judgments OpenRig | Численный отчет и experiment ID как доказательство |
| Финансовые запуски и данные | Реестр сервиса и immutable artifacts | Новые предметные записи: dataset, protocol, strategy, run, result |

Сервису нужны состояния `job queued/running/failed/completed`: это состояние вычисления, не состояние работы агента. Один qitem может относиться ко множеству jobs. Job completion не закрывает автоматически qitem и не принимает финансовый вывод.

Агентная ответственность и состояние команды наблюдаются в интерфейсе OpenRig, без отдельного командного экрана финансового dashboard. Если будущему сервису потребуются ссылки на назначения, они читаются из поддержанного интерфейса OpenRig, без собственного редактирования. Нет второй таблицы agent tasks, очереди reviewer assignments, standalone STATUS.md или общего растущего MEMORY-log.

Предварительное исследование также не создает отдельную память: source/hypothesis cards находятся в evidence конкретной mission/slice и адресуются устойчивыми `SRC-###`/`HYP-###`. Компактный `INDEX.md` — навигационная проекция, не журнал и не новый источник истины. Его можно восстановить из карточек; содержимое карточек не копируется в NOTES, LEARNED или queue bodies.

## Формат опыта

Каждый эксперимент регистрируется инструментом структурированно; числа и конфигурации не переписываются агентом вручную. Нужны ID, связи и метаданные из [PLATFORM.md](PLATFORM.md).

Проверяемый вывод имеет:

- краткое утверждение и его область: рынок, период, данные, горизонт, условия;
- идентификаторы экспериментов/отчета/протокола;
- основания, контрпримеры и ограничения;
- статус знания, дату и владельца, условие пересмотра;
- ссылку на замененный вывод при исправлении.

Процедурный вывод живет в `LEARNED.md` владельца; объемное доказательство остается в experiment artifacts. Продуктовый факт — в документации сервиса рядом с версией кода. Не создавать независимый «knowledge graph» как обязательную третью истину. Поисковый индекс по этим материалам — перестраиваемая проекция, не место редактирования вывода.

Пример смысла: «источник X не дал добавочного эффекта в Y при Z; E-104…E-118; вернуться при появлении доказуемого publication timestamp», а не «X бесполезен навсегда».

## Владельцы

Каждый seat поддерживает собственный `LEARNED.md` в своих словах. Lead отвечает за краткие общие знания рига, а не редактирует личный опыт всех. На уровне pod владелец определяется нативной топологией; дополнительный lead-seat не нужен.

Architect поддерживает технический план и решения в существующих mission/slice артефактах; назначения остаются в native queue, без нового трекера. Validator подтверждает финансовый смысл вывода; QA Code — корректность реализации, QA System — поведение собранной системы. Platform Engineer реализует запись, поиск и измерение контекста; DevOps — сохранность и восстановление. Отдельный memory librarian не вводится.

Карточку гипотезы ведет ее автор, карточку источника — исследователь источника. Коллеги добавляют адресуемые замечания, сохраняя автора и provenance каждого утверждения. Компактный `INDEX.md` — восстанавливаемая навигация, а не approval gate: любой владелец нового материала обновляет соответствующую строку, и ожидание Lead не блокирует чтение, поиск, новую карточку или следующий ограниченный research step.

Непрерывность проекта не означает непрерывно растущий контекст. Источники и гипотезы остаются компактными адресуемыми карточками с устойчивыми ID; `INDEX.md` является навигацией и обновляемой проекцией текущих выводов, а immutable evidence завершенных итераций сохраняется отдельно. Новая итерация извлекает только релевантные карточки и предыдущие решения, не загружает всю историю и не создает отдельную БД, RAG, task tracker или общий журнал памяти.

Не создавать заранее фиктивные LEARNED от имени будущих occupants. Оператор доставляет обязанности через role guidance, а каждый реальный seat заполняет собственную нативную память при работе.

## Обязательные бюджеты

Это локальная политика финансового проекта, а не заявленная встроенная настройка OpenRig. Оператор реализует ее на доступном уровне harness/context loader и проверяет эффект. Если механизм не умеет измерять или ограничивать загрузку, записать пробел; нельзя обещать автоматическое соблюдение только текстовой инструкцией.

| Загружаемый слой | Максимум токенов на одно рабочее представление |
|---|---:|
| Общая культура, intent и действующие обязательные правила | 3 000 |
| Ролевая guidance и относящаяся цепочка LEARNED | 3 000 |
| Текущий qitem/scope, краткий checkpoint и continuation | 2 000 |
| Результаты поиска и выбранные фрагменты доказательств | 4 000 |
| Сумма проектной памяти | 12 000 и не более 20% доступного context window модели |

При меньшем context window пропорционально уменьшается загрузка вспомогательных материалов; обязательный смысл не обрезается. Если обязательные части не помещаются, нужен более компактный профиль либо подходящая модель до запуска этого seat. Нельзя скрыто убирать ограничения риска/полномочий.

Инструкции harness, определения tools, общая переписка и выдача команд считаются отдельно в полном context usage. После достижения 65% доступного окна — подготовка восстановления; до 75% — поддержанный runtime/OpenRig переход или compaction с проверкой восстановления. Если harness не дает usage, отображать оценку и conservative estimate, а не выдуманный точный процент. Нативный более ранний порог имеет приоритет.

Точное измерение — tokenizer выбранной модели, когда доступен; оценка маркируется estimate и имеет запас. Суммируется весь реально переданный материал, включая повторные system/managed фрагменты и цепочки предков, а не только размер одного файла.

Полная спецификация не автоподгружается всем seats. Минимальный общий boot: intent из `SPEC.md`, `CULTURE.md`, бюджет/authority правила и указатели. Затем конкретная роль в `TEAM.md` и адресованные разделы своего контракта. EVALUATION целиком нужен Validator; остальные получают обязательные правила и нужную часть. Индексы и история — по запросу.

## Рост и консолидация

- Запись полного результата выполняет инструмент. Одно событие не создает двенадцать пересказов.
- В LEARNED добавляется только новое знание с причиной; новый успех того же типа дополняет ссылку на основания.
- При достижении бюджета владелец дистиллирует актуальный раздел и переносит подробности в адресуемые evidence/NOTES. История исправлений сохраняется через версионирование; оперативная сводка остается короткой.
- Deposit перед handover/clear и завершение кампании — естественные точки консолидации. Нет повторных таймерных сообщений «перечитай все».
- Транскрипты и raw logs не подмешиваются в boot. Они используются адресно для расследования.
- Отрицательные эксперименты не удаляются ради красоты каталога или экономии контекста.

Для всего локального Polar действует единый64GiB storage ceiling, включая уже сохраненные evidence/archives/backups/scratch/logs; перед кампанией задаются правила retention внутри этого общего total, без дополнительных retained/scratch/UI subcaps. Минимальные метаданные всех попыток, final evidence, протоколы, зависимости принятых/отвергнутых выводов и validation receipts сохраняются. Воспроизводимые тяжелые промежуточные файлы можно убирать по согласованной политике после проверки отсутствия retained ссылок. Не удалять все старые артефакты по возрасту.

## Поиск

Перед новой гипотезой инструмент ищет похожие попытки по dataset, рынку, семейству сигнала, периоду и механизму; дополнительно возможен полнотекстовый/семантический поиск.

Выдача: не более 10 кратких записей за запрос, с ID, выводом, областью применимости и ссылкой. Нужные детали раскрываются порциями в пределах retrieval budget. Для important negative results есть точные теги и триггеры, а не только embeddings. Ошибка поиска отличается от «совпадений нет».

Не загружать результаты закрытого holdout или недоступные другому seat данные через память. Search/embedding индексы, logs и dashboard соблюдают те же границы доступа, что исходный evaluator.

## Восстановление

Использовать нативные identity, очередь, LEARNED, scope NOTES и поддержанные handover/compaction процедуры OpenRig. Continuation ссылается на experiment/job ID и следующую проверку; не создает вторую оперативную память.

Свежий occupant подтверждает собственную identity, актуальное назначение и последнюю подтвержденную точку, проверяет фактическое состояние job, затем продолжает. Незавершенная операция после timeout считается неопределенной до проверки; нельзя слепо запускать дубликат. Сбой/неполное подтверждение восстановления блокирует затронутый seat и зависимые действия, а не независимую работу всей команды. Противоречивый флаг сверяется с session binding, checkpoint и историей назначений; нерешенная неопределенность передается оператору с конкретным основанием.

## Измерение и приемка

DevOps/Platform собирают токены загружаемых слоев, долю estimates, storage, latency поиска, долю oversize выдач. Исследовательские владельцы и Validator смотрят на необоснованные повторы опытов, выводы без evidence и устаревшие заключения; Lead получает сводный статус только по запросу.

QA System воспроизводит следующие ситуации; QA Code отдельно проверяет unit/компонентные контракты записи, поиска и бюджета:

1. После большого числа синтетических записей история растет, но boot и retrieval остаются в лимитах; число записей теста и фактические токены показаны.
2. Свежий occupant находит ранний отрицательный результат по новой похожей задаче и объясняет, что оправдывает повтор.
3. После остановки восстанавливается текущая OpenRig assignment и ровно тот же job; не создается вторая task state.
4. Замена вывода не оставляет старую сводку действующей; evidence старой версии доступны.
5. Вывод проверяется по исходным данным/конфигурации; ссылки не потеряны после архивирования.
6. Недоступный holdout не обнаруживается через поиск, логи или память.

Провал retrieval/restore означает дефект системы памяти, даже если файлы физически существуют. Эти проверки специфицированы, но еще не выполнены.

## Пользовательские решения и UI-запросы

Исходный UI-запрос или иной вопрос, действительно требующий пользовательского решения, хранится в native qitem оператору; основания — в существующих артефактах по ссылкам. Пользовательское решение связывается с фактически доставленным вопросом через существующий human-decision маршрут; разрешенное поручение UI-ригу — отдельное связанное назначение. Не создавать отдельный backlog, таблицу approvals или растущий журнал запросов. Компактный список для напоминания — восстанавливаемая проекция qitems, фактических доставок и явных решений.

Технические состояния очереди и `external:user-*` без фактически показанного вопроса не являются доставкой; доставка/просмотр/обсуждение не равны одобрению/отклонению. Исходный qitem может быть закрыт передачей, а решение оставаться не принятым; список напоминаний учитывает всю связанную цепочку. Явно одобренные без поручения передачи UI-запросы сохраняются как одобренные, но не переданные; они не относятся к ожидающим рассмотрения. История и отклоненные предложения сохраняются, не подменяются новым запросом без нового основания.

Обязанность оператора после каждого обращения пользователя напоминать обо всех нерешенных вопросах Polar, действительно требующих пользовательского решения и блокирующих зависимый результат, закрепляется в его постоянных проектных инструкциях/standing duties с указателем на этот контракт. Она восстанавливается при handover вместе с существующими qitems и фактами доставки; не хранить единственный список в контексте разговора и не править shipped skill ради одного проекта. Повторное напоминание не создает новый запрос; периодический вызов оператора вне обращений пользователя не вводится.

HYP card is economic-candidate truth; revisions of one claim deduplicate, distinct strategy/data/risk interventions do not. Live RESERVED envelopes count immediately. ## Исследовательский результат, data gap и прямое владение

Одна линия HYP имеет author-owned актуальную карточку/протокол со ссылками на history/источники/peer corrections. Независимые выводы и версии сохраняются, но отдельная формула/review/передача не создают новый slice автоматически. Конечный qitem задает ограниченный рабочий шаг внутри slice; proof удостоверяет содержательный результат, а не количество созданных scopes. Исторические scopes не удаляются и не получают переписанный verdict; восстанавливаемая навигация объединяет связанные материалы по HYP.

Data gap связывает HYP с существующими или новыми DR/DE qitems, требуемым покрытием, источниками/альтернативами, import/quality evidence и поставленной dataset revision либо точной внешней причиной/владельцем/возобновлением. Статус BLOCKED без передачи устранимого data gap владельцам не является достаточным результатом. Нового трекера не требуется. Research summaries/протоколы остаются у исследователей и Validator, не требуют доставки/одобрения Lead. Он может получить состояние по запросу.

QA-led технические judgments и scientific Validator verdict сохраняют отдельные полномочия. При изменении процесса обновляются действующие native judges/назначения поддержанным способом, исторические receipts не переписываются. Подготовленная инструкция не доказывает, что native policies или runtime уже обновлены.

## Общий опыт доступа и проверенные маршруты

Файл ~/.openrig/shared-docs/access/NOTES.md — общий предметный опыт доступа для работающих в разрешенном scope агентов. Он не заменяет native queue, научные source rights/fitness отчеты или credential storage. Оператор поддерживает адресуемость/указатель; исполнитель дописывает эпизод без Lead/операторского approval. В начале компактные provider routes с наблюдаемыми предпосылками, рабочими шагами, версией/датой проверки, состоянием подтверждения и ссылками; далее сохраненные события/исправления. Файл не загружается целиком в каждый boot: читать route/последние релевантные события порциями в действующем retrieval budget.

Каждый настоящий access-эпизод имеет event_id, actor/qitem, outcome/evidence, явные new/unusual/blocking/missing-tools/user-action и проверяемый следующий шаг. Это регистрация, login/reauth, session recovery, создание/обновление credentials, проверка новых прав либо проблема доступа с ее разрешением. Обычные GitHub/PR/merge/API операции через уже работающую авторизацию не записываются; их proof остается в штатной работе. Повторный login без осложнений записывается кратко. Несколько попыток устранения одной проблемы объединяются. Существенные checkpoints сохраняются до handover. Дописывать событие без переписывания чужих записей; после неопределенного результата записи сначала проверить event_id. Историю не удалять ради краткой инструкции; ошибочный диагноз исправлять датированной связанной записью. Наблюдаемую работу конкретного launch path не обобщать до доказанной причины или универсальной совместимости.

В общем файле нет имен/email/password/keys/cookies/verification codes или token-bearing URLs, private page dumps/headers, keystroke contents либо credential material. Допустим несекретный alias и ссылка на безопасный отчет; чувствительные файлы — только в уже разрешенном private location, не shared journal/Git. Профиль pacing содержит интервалы/безопасные flags, не введенные значения. Скриншот/trace перед включением evidence проверяется на содержимое; отсутствие секретов в основном MD не делает raw trace безопасным.

По запросу пользователя оператор/назначенный аналитик анализирует накопленные эпизоды: повторяемые причины/пробелы инструментов, фактические обращения к человеку, задержки и покрытие методов; связывает предложения с event IDs и инженерными задачами DevOps/PE. Записи не создают автоматический проект или ticket на каждый click. Срочный настоящий blocker разрешается через текущий qitem независимо от последующего ретроспективного анализа. Только подтвержденный новый способ или существенное уточнение меняют краткий рабочий route; routine success его не раздувает. Прежние routine GitHub-записи сохраняются и при следующем обслуживании переносятся из рабочего обзора в historical, без переписывания истории.

Оптимизация текущих access-инструментов и необходимая замена adapter по конкретному ограничению получают инфраструктурный приоритет v0.27 до фактического применения. Наличие альтернативы или успешный исторический эпизод сами по себе не требуют миграции; сохраняется связанный с задачей scope, без отдельного журнала/согласования.

## v0.19 — Import state и точность диагностических записей

Job progress/retry counters/checkpoints и terminal manifests принадлежат загрузчику и существующему private artifact storage, не растущему Markdown или новой агентской очереди. Native queue хранит владельца/назначение/передачу, import state — выполнение. В Markdown остаются существенные причины/решения и ссылки на attempts/manifests, не отчет на каждый batch. Успехи, no-match и ошибки прежних проходов сохраняются с атрибуцией; версии request semantics/cache keys определяют допустимое переиспользование. При restore читать актуальный checkpoint/итог и релевантные ошибки, не всю историю. Ключи и source data не входят в процессный/access-журнал или публичный Git.

В существующем process-health/NOTES.md при существенной находке разделять observed symptom, подтвержденное влияние/incident и cause с уровнем подтверждения. Единичный терминальный индикатор не повышать до текущего сбоя без свидетельства влияния. При закрытии добавлять доказательство восстановления работы и отдельно статус исправления причины; повторения связывать с исходной проблемой. Ошибочный вывод исправлять датированным дополнением рядом/по ссылке, сохраняя исходную запись. Не писать каждый transient symptom или здоровую проверку, не создавать новый журнал/БД/трекер. Сводки различают число причин, эпизодов и наблюдений, не складывают их в одно число сбоев.
